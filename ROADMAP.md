# Transpo — Roadmap (tranches verticales)

Chaque tranche livre du fonctionnel réel et passe la **Definition of Done** (`DEFINITION-OF-DONE.md`) avant merge : tout via Docker, tests (dont **E2E**), i18n FR/AR + RTL, isolation tenant, doc à jour. Séquencé par dépendances — réordonnable ; une tranche trop grosse peut être scindée.

Légende : ✅ fait · 🚧 en cours · ⏳ à venir · *(skeleton)* = livré au niveau squelette, non validé au run.

## Phase 0 — Fondations
- [x] **T0 — Amorçage mono-repo** ✅ *validé Docker* — Docker, Postgres schema-per-tenant, `packages/domain`, API NestJS (`/health`, `GET /v1/orders` isolé, `TenantGuard`).
- [x] **T1 — Couche données réelle** ✅ *validé Docker* — `packages/db` Drizzle, migrations platform + boucle tenants, `provisionTenant`, seed ; API branchée. Vérifié en conteneur : isolation casaexpress(2)/atlas(1), 400 sur tenant inconnu/absent.
- [x] **T2 — Auth, RBAC & durcissement multi-tenant** ✅ *validé Docker (E2E 10/10)* — login tenant + super-admin (argon2id), JWT {sub,role,tenant}, JwtAuthGuard/RolesGuard/@Roles, TenantGuard durci (claim JWT, anti cross-tenant), audit `platform.audit_log`, provisioning tenant (SUPER_ADMIN). 2FA/SSO-SAML : écrans posés côté maquette, à câbler ultérieurement. — `transpo-auth-security`
- [~] **T3 — Packages partagés** 🚧 — `@transpo/design-tokens` (échelle Radix, source unique web+RN) et `@transpo/api-client` (typé) : ✅. **`@transpo/i18n` : socle refait et appliqué** (2026-08) — le package existait mais n'était importé nulle part, les 24 pages étaient en français codé en dur. Dictionnaire par espaces de noms avec repli sur le français, langue résolue côté serveur (cookie) et `lang`/`dir` posés sur `<html>` au rendu, bascule de langue dans la topbar. **Converti : navigation, topbar, rôles, login, tableau de bord.** Reste : les 22 autres pages console, le portail marchand, la console SaaS et les 7 écrans mobiles. — `transpo-design-system`, `transpo-i18n`

## Phase 1 — Cœur opérationnel (Console transport)
- [x] **T4 — Console web (shell complet + écriture)** ✅ *validé Docker (Playwright 9/9)* — shell fidèle à la maquette (sidebar groupée + topbar recherche/thème/avatar, indigo/slate, clair/sombre), **tenant résolu par le host** (sous-domaine, plus de saisie). **21 écrans** branchés à l'API, **fonctionnels en écriture** via un proxy authentifié : Commandes (création/assigner/avancer/annuler/encaisser + détail timeline), Fraude (arbitrage), Retours (reprogrammer/rendre), Tournées (créer/avancer), Zones/Véhicules (créer), PC flotte (géofence), Notifications (envoi), + Dispatch, Analytics, Caisse, Reversement, Factures, Tarification, Avis, Modèles, Utilisateurs, Paramètres, Hub. Servie en **build de prod**. — PRD-01
- [~] **T5 — Dispatch & zones** 🚧 *backend validé Docker* — zones (CRUD) + suggestion de livreur (score /100) ; carte temps réel + PostGIS à venir avec l'UI. E2E API. — `transpo-maps-geo`, `transpo-realtime`
- [~] **T6 — Flotte** 🚧 *validé en prod* — véhicules (CRUD + conformité assurance/CT) ; **chauffeurs complets** : module API dédié (CRUD, disponibilité, renouvellement permis/visite médicale, rattachement d'un véhicule du parc, suppression gardée par les commandes en cours), conformité + perf dérivée des commandes, page console fidèle (KPI, alerte, filtres, actions). Le dispatch exclut les permis/visites expirés. EU 561 / objectifs à venir. E2E API.
- [~] **T7 — Tournées** 🚧 *backend validé Docker* — planificateur multi-arrêts (regroupe commandes + assigne livreur), réordonnancement, cycle PLANIFIEE→EN_COURS→CLOTUREE, `@Roles ADMIN/DISPATCHER`. **Vrai moteur de routing** (optimisation d'ordre) : à compléter. E2E API. — `transpo-maps-geo`

## Phase 2 — Terrain (App livreur, offline-first)
- [~] **T8 — Livreur socle** 🚧 *backend validé Docker + app RN* — login DRIVER (claim `driver`), missions (commandes actives scopées), statut séquentiel, **idempotence offline** (Idempotency-Key → pas de double effet au rejeu). **App mobile Expo/React Native** (`apps/driver-app`) : écrans login/missions/mission branchés à l'API, packages partagés, typecheck en CI. Reste : onboarding, scanner natif, offline-store persistant, E2E Maestro (device requis). — `transpo-offline-sync`
- [~] **T9 — Livreur preuve/COD/caisse** 🚧 *validé en prod (API + console)* — preuve de livraison + encaissement COD → LIVREE (idempotent), ownership vérifié. **Le `proofLevel` est désormais appliqué** : photo et/ou signature exigées selon les 4 niveaux, artefacts validés (data URI, type, taille ≤ 700 Ko) et stockés (`delivery_proofs`, migration 0024) ; `GET /v1/orders/:ref/proof` les expose et la console affiche les vrais artefacts (la tab montrait 4 carrés factices). **Capture côté mobile : à faire** — l'app n'a ni caméra ni pavé de signature, elle ne peut donc plus livrer une commande de niveau photo/signature. Ma caisse/dépôt, shift EU 561 : à compléter. E2E API.
- [~] **T10 — Livreur annexes** 🚧 *validé en prod* — signalement d'incidents (livreur) + traitement (ops), chat support bidirectionnel livreur↔ops, historique & gains (livraisons × forfait). **Écrans mobiles livrés** (incidents, support, gains) : l'app couvre 7 des 9 routes livreur. Envoi direct sans file d'attente pour ces trois-là — l'API ne déduplique ni incidents ni messages, un rejeu créerait des doublons. Tournée mobile : à compléter. E2E API.

## Phase 3 — Argent & flux inverses
- [~] **T11 — Cash & COD** 🚧 *backend validé Docker* — encaissement COD, réconciliation par livreur (théorique), reversement marchand (net=brut−commission). Dépôt/écart/remboursement : à compléter. E2E API.
- [~] **T12 — Retours & hub** 🚧 *backend validé Docker* — échec livraison → retour A_TRAITER, reprogrammation (plafond MAX_RETURN_ATTEMPTS=3), renvoi marchand → RENDU. Tri hub/manifeste : à compléter. E2E API.
- [~] **T13 — Facturation & tarification** 🚧 *backend validé Docker* — devis (cascade à 3 niveaux + TVA), factures marchand dérivées (commission/TVA). Litiges/modes prépayé-postpayé : à compléter. E2E API.

## Phase 4 — Marchand & Client
- [~] **T14 — Portail marchand** 🚧 *validé en prod* — vues scopées au marchand (claim JWT `merchant`, résolu serveur) : dashboard (KPIs), commandes, portefeuille (net = COD − commission), facture dérivée. `@Roles MERCHANT`. **Portail web livré** (`/portail`, shell dédié) : tableau de bord, mes commandes (recherche + filtres), portefeuille (détail par commande + COD restant à collecter), facture évolutive. Routage par realm : la console transport renvoie un MERCHANT vers son portail. API/webhooks signés + mode facturation : à compléter. E2E API. — PRD-02
- [~] **T15 — Client final** 🚧 *backend validé Docker + app RN* — suivi public sans compte (timeline par code, tenant dans l'URL) + notation post-livraison (1..5, verrouillée). **App mobile Expo/React Native** (`apps/client-app`) : accueil (saisie code) + suivi (timeline + notation étoiles), branchée aux endpoints publics, **build EAS** (projet Expo `transpo`, profil preview/APK). Côté console, **page Avis** dédiée (`/v1/reviews`) : distribution 1..5, moyenne, avis négatifs, moyennes par livreur et par marchand, filtres. Reste : live tracking carte, créneau, chat, push. E2E API. — `transpo-realtime` (+ push)

## Phase 5 — Pilotage & SaaS
- [~] **T16 — PC flotte temps réel** 🚧 *validé en prod* — ingestion de positions livreur, snapshot live (dernière position/livreur), **géofencing** (haversine) + alertes sortie de zone. **L'app livreur alimente enfin le PC flotte** : suivi expo-location au premier plan, sans file d'attente (une position est périmée dès la suivante), interrupteur explicite et mémorisé côté livreur. Realtime en polling REST ; WebSocket + suivi en arrière-plan : à câbler. E2E API. — `transpo-realtime`, `transpo-maps-geo`
- [~] **T17 — Analytics/SLA & Fraude COD** 🚧 *backend validé Docker* — synthèse (successRate, byStatus) ; fraude : scoring (fraudScore), liste, leaderboard livreurs à risque, revue humaine (enquête/blanchir/confirmer) audité, `@Roles ADMIN`. Tableaux par zone/marchand : à compléter. E2E API.
- [~] **T18 — Console SaaS** 🚧 *validé en prod* — tenants (provisioning réel schema-per-tenant), catalogue de plans, changement de plan, facturation plateforme (montant + usage/quota), **paywall** (statut SUSPENDU bloque le login, vérifié de bout en bout). **UI console SaaS livrée** : realm plateforme au login (`?realm=saas`), section `/saas` avec shell dédié gardé par le rôle — organisations (KPI + revenu mensuel, filtres, provisioning, changement de plan, activation/essai/suspension), facturation (montant, consommation vs quota, dépassements), plans (catalogue + répartition du parc). Reste : **déprovisionnement** (on peut créer un tenant, jamais le retirer) et abonnements Stripe. E2E API. — PRD-05
- [~] **T19 — Notifications** 🚧 *validé en prod* — **modèles bilingues FR/AR persistés par tenant** (édition FR/AR avec aperçu et variables, transactionnel/marketing, activation, événements propres au tenant, rétablissement de l'original) ; l'envoi résout le modèle en base, un modèle désactivé bloque l'événement. Canaux SMS/WhatsApp/push/email, **consentement 09-08** (transactionnel exempté, marketing bloqué sans opt-in, saisie de l'opt-in depuis la console). Centre de notifs filtrable avec motif de blocage et **rejeu** d'un envoi bloqué. Passerelles réelles (envoi effectif) : à câbler. E2E API.

## Phase 6 — Durcissement & mise en prod
- [~] **T20 — Sécurité/conformité/observabilité** 🚧 *backend validé Docker* — journal d'audit lisible (SUPER_ADMIN), droits des personnes RGPD/09-08 (export + effacement/anonymisation tracés), anti-bruteforce login (429). **Cloisonnement des rôles corrigé** (2026-08) : les lectures d'exploitation n'avaient aucun `@Roles` au niveau classe — un MERCHANT ou un DRIVER du tenant lisait toutes les commandes (dont celles des marchands concurrents), la liste des comptes console et le roster livreurs avec téléphones et permis. `CONSOLE_ROLES` posé sur les douze contrôleurs concernés ; Analytics et Avis déclaraient des rôles sans `RolesGuard`. Monitoring/perf + page confidentialité : à compléter. E2E API.
- [~] **T21 — CI/CD & déploiement** 🚧 *pipeline validée Docker (répétition locale : typecheck + E2E API 83/83 + Playwright 2/2)* — GitHub Actions : build stack, typecheck workspace, suite E2E API complète, Playwright, teardown ; garde de concurrence. Registry/déploiement multi-env + Maestro (mobile) : à compléter. — `transpo-testing`, `transpo-git-workflow`
